# Simulation in moveHMM, momentuHMM, hmmTMB — survey for `simulate(mod)` in LaMa

Versions read: moveHMM 1.11, momentuHMM 1.5.8, hmmTMB 1.1.2 (installed CRAN versions; source printed from the
installed namespaces, docs via `tools::Rd2txt`). Statements marked **[tested]** were reproduced by a small
script, **[guess]** are my inference. GitHub issues were read via the public API.

Sources:
- moveHMM: `moveHMM::simData` (`R/simData.R`), `?simData`
- momentuHMM: `momentuHMM::simData`, `simHierData`, `simObsData` (`R/simData.R`, `R/simHierData.R`, `R/simObsData.R`), `?simData`, vignette Eq. 1
- hmmTMB: `HMM$simulate()`, `MarkovChain$simulate()` (`R/hmm.R`, `R/markov_chain.R` [guess for the file name]), `Dist$rng_apply()`; `HMM$check()` is the in-package use; `inst/simulations/*` are the in-package simulation studies

## Comparison table

## Per-package notes

### moveHMM (`simData`)
- Time loop per animal: `Z[1] ~ uniform`; for `k = 2..nbObs`: `gamma` built from `beta` and `covs[k, ]`, `Z[k] ~ gamma[Z[k-1], ]`. Observations for step `k` come from state `Z[k]`, location advances `X[k] → X[k+1]`; last step/angle are NA.
- With `model`: parameters from `model$mle`; `covs` from `model.matrix(model$conditions$formula, model$data)` (transformed columns such as `cos(cov2)` are returned as covariates **[tested]**); `nbAnimals`/`obsPerAnimal` still default to 1 / 500–1500, so the fitted design is not reproduced unless the user passes them.
- Pitfalls: (i) `delta` always uniform; (ii) covariate recycling; (iii) NA-handling for `covs` is broken: it references `trackData` before it exists, so `covs` with NA stops with `object 'trackData' not found` **[tested]**; (iv) random `beta` if missing (`rnorm`); (v) no state-dependent covariate effects.

### momentuHMM (`simData`, `simHierData`, `simObsData`)
- Same skeleton as moveHMM but generalised; heavy parameter bookkeeping (`checkInputs`, `n2w`, `w2n`, `getDM`). When no path-dependent covariates are used, the parameters for all rows and animals are computed once (`fullsubPar`) and the loop only draws states and observations; with `spatialCovs`/`centers`/`centroids`/`angleCovs`/`rw_*` the parameters are recomputed **inside** the loop from the simulated positions (so slower: the help page says so).
- `model` interface: reuses `model$conditions` (bounds, DM, formulas, zero inflation), estimates from `model$mle`/`model$mod$estimate`, and covariates `model$data[covsCol]` (all covariates used in any formula or DM). Everything else except `nbAnimals`, `obsPerAnimal`, `states`, `initialPosition`, `lambda`, `errorEllipse` and `covs`/`spatialCovs`/`centers`/`centroids` (replacement covariates) is ignored (`?simData`, argument `model`). Replacement covariates are taken consecutively, **not matched by ID**, and recycled if too short (documented).
- Reproducing the observed design requires `nbAnimals = nlevels(ID)` and `obsPerAnimal = as.list(table(ID))` (from the code; untested): the default simulates one animal of random length.
- Initial distribution: see table; per-animal covariates in `formulaDelta` are evaluated at the animal's first row, `formulaPi` too (help: "only the covariate values corresponding to the first time step for each individual ID are used").
- Spatial: coordinates are assumed Cartesian; leaving the raster extent is an error unless `retrySims > 0` (whole data set re-simulated; maintainer declines accept/reject because it biases the draws, issue #20). `initialPosition` default (0,0) must lie in all rasters. Lat/long not supported (issue #20).
- `states = TRUE` appends the true states; `ncores` parallelises over animals (doRNG).
- Hierarchical: `simHierData` mirrors `simData` with `Node` objects per level (not surveyed in detail).

### hmmTMB (`HMM$simulate`, `MarkovChain$simulate`)
- `HMM$simulate(n, data)`: (1) `hid$simulate(n, data = obs$data(), new_data = data)` draws the states, (2) `obs$make_mat(new_data = data)` builds the design matrices for the new covariates, (3) `par_obs[, state, i]` gives the parameters of row `i` in the drawn state and `Dist$rng_apply(n = 1, par)` draws the observation, one stream at a time. Temporarily swaps in the new design matrices and restores them afterwards.
- Tracks: `ID` column; new track whenever `ID[i] != ID[i-1]`; if `data` has no `ID`, a single track is assumed. Track-specific covariates are ordinary columns.
- Covariates are required: simulating without `data` for a model with covariates fails inside `predict.gam` (`object 'x' not found`) **[tested]**.
- Random effects and smooths are handled inside the same machinery as in fitting; simulation conditional on the current coefficient values (the fitted posterior modes) unless the user overwrites them.
- Pitfalls: stale `delta0` (above); the number of new IDs is limited to the number of fitted IDs; ID order (issue #51 shows ID-order and `tpm[,,t]` vs `tpm[,,t-1]` bugs in the decoding layer, fixed in 951f706, b114c64, a3791e0, 52592ab; `simulate` segments by order of appearance, so it should be unaffected [guess]); the observation loop is a plain R loop over rows per stream (slow for large `n`, my reading).

## Common pattern across the three packages

1. State chain simulated first (or interleaved when covariates depend on the path), observations drawn afterwards given state and row-wise parameters; streams conditionally independent.
2. The user-facing "simulate from fit" is a thin layer over stored formula objects (`formula`, `DM`, `model.matrix`) that can be **re-evaluated for new covariate values**. This is exactly what LaMa does not have (the mapping covariates → Gamma/parameters lives in the user's nll).
3. Replacing covariates is allowed everywhere, but initial distribution (hmmTMB: stored, momentuHMM: from first row) and design (momentuHMM: recycling; hmmTMB: ID count) are the places where it goes wrong.
4. Only momentuHMM supports covariates that depend on the simulated path, via an explicit sequential loop and by understanding the model structure (`DM`, `centers`, `spatialCovs`).

## Implications for LaMa

LaMa's `forward()` reports `delta` (per track), `Gamma` (matrix / per track / nObs slices / periodic with `tod`), `trackID`, and now `streams` (data, density name, natural-scale parameters with scalar, per-state or `nObs × nStates` shape). `Gamma.slice(gidx[t])` is the transition *into* `t` (`src/forward_algorithms.cpp:10`), and the first observation of each track uses `delta` directly.

1. **Default = observed design, no covariate input needed.** This is the case all three packages support robustly (hmmTMB's `check()`, momentuHMM with explicit `nbAnimals/obsPerAnimal`). LaMa has it for free because the recorded `Gamma`, `delta`, parameters and `trackID` already are the covariate-evaluated, track-specific quantities. Simulating "the same design" then needs no covariates, no formula machinery and no recycling logic. Suggestion: make this the only documented mode in the first version; it covers parametric bootstrap, simulate-and-refit, and GOF by simulation (hmmTMB's `check()` pattern).

2. **New covariates / tracks.** Not derivable from recorded quantities (no formulas). Options (design suggestions, not from the packages):
   - (a) not supported, say so in the docs;
   - (b) *re-evaluate the user's likelihood*: `simulate()` takes the same reported list that `viterbi()` etc. take, so for new covariates the user rebuilds `MakeADFun` with the new data, calls `obj$report(par_hat)`, and passes that. This reproduces what momentuHMM/hmmTMB do with new `covs`/`data` without LaMa knowing the covariates; the track structure, `Gamma` slices and parameters then come from the user's own function. I would document this as the recipe and not build more.
   - Do **not** copy momentuHMM/moveHMM's silent recycling; a changed number of observations should be an error, because parameters recorded as `nObs × nStates` matrices are tied to rows. If the length differs, only homogeneous `Gamma`/scalar-or-per-state parameters can be re-used (then `trackID`/lengths could be overridden, e.g. `n = c(100, 200)`); that restricted case seems cheap to support (guess: nobody will ask for it initially).

3. **Initial distribution.** Draw `Z_1 ~ delta[track, ]` using the same `delta` normalisation as `prepare_decoding()`. LaMa's `delta` is the distribution of `Z_1` (like hmmTMB, unlike momentuHMM's `delta Gamma_1`). Because LaMa records `delta` at the time of the likelihood evaluation on the data, the hmmTMB staleness problem (stored `delta0` not updated for new covariates) does not arise as long as simulation uses the reported `delta`. For `delta = stationary(Gamma)` with time-varying `Gamma` the reported `delta` is whatever the user passed to `forward()`; nothing to do.

4. **Time indexing.** Reuse the exact `gidx` and track-start logic from `prepare_decoding()`/`prepare_forward()`, as planned. The packages show two different conventions (moveHMM/momentuHMM: row `k` covariate drives `k-1 → k`, same as LaMa; hmmTMB: `tpm[,,t]` is `t → t+1`) and hmmTMB's issue #51 is a reminder that off-by-one errors with time-varying tpm go unnoticed. Suggested test: simulate long series from a model with `nObs` slices of strongly different `Gamma` and compare empirical transition frequencies per slice with `Gamma[,,t]`; plus simulate-then-`viterbi` accuracy and equality of the log-likelihood code path on the simulated data.

5. **Tracks.** Use `trackID` as is (consecutive blocks, appearance order, as in the forward algorithm); do not re-derive order from factor levels (the hmmTMB ID-order bug class). Track-specific `delta`/`Gamma` come from the reported shapes. Lengths are those of the observed tracks.

6. **Path-dependent covariates (distance to centre, rasters, lagged observations).** Only momentuHMM does this, by recomputing covariates and parameters at every step. In LaMa such covariates are computed by the user from the *observed* data inside or outside the nll, so the recorded parameter matrices contain the *observed* values; `simulate()` would therefore draw "conditionally on observed covariates" and never reproduce feedback from simulated data. That is correct for covariates that are exogenous (time of day, temperature) and wrong for endogenous ones. I'd state this in the docs. Real support would need a sequential callback (user supplies `update(sim_so_far, t) -> parameters`), which is a different, larger design; I would defer it (momentuHMM's `simData` is >1400 lines, most of it for this). Related: reconstructing `x, y` from simulated step/angle is a post-processing step of the user's choice; none of the generic building blocks in LaMa knows about locations (moveHMM/momentuHMM bake it in, hmmTMB does not offer it).

7. **Random effects.** With `qreml`/RTMB random effects the recorded `Gamma`/parameters contain the *estimated* random effects. So `simulate()` is conditional on them, like hmmTMB's default and unlike momentuHMM's `mixtures`, which draw the discrete random effect per animal. A full parametric bootstrap with fresh random effects is not possible from the recorded quantities. Document.

8. **Densities → random generators.** momentuHMM maps `dist` name to `r<name>`, hmmTMB stores the generator in the family object. LaMa records the density's name (`name = deparse(substitute(dens))`). Suggest: look up `sub("^d", "r", name)` (LaMa has `rvm`, `rwrpcauchy`, `rskewnorm`; whether an `rgamma2` exists I did not check), allow an explicit `rdens`/`sim` argument per stream or per call for user-defined densities, and error clearly otherwise. Argument conventions for r-functions (`n` first, same parameter names) must be checked; `gamma` in momentuHMM needs mean/sd → shape/rate conversion by hand, the same is needed for `dgamma2`/`rgamma2` pairs. Circular streams must be wrapped to the same range as the data (momentuHMM wraps manually to (−π, π]; `rvm(wrap = TRUE)` in LaMa).

9. **Zero inflation, mixtures within a state, several streams.** Nothing special if the recorded density is the user's full density: the simulation just needs the matching generator for that density (e.g. a user-defined `dzigamma`/`rzigamma`); momentuHMM's draw-mass-then-density approach and hmmTMB's dedicated families are equivalent. Several streams are drawn independently given the state, as in all three packages.

10. **Missing data.** None of the packages inserts missing observations when simulating. Suggested option for LaMa: simulate all rows, then optionally copy the observed NA pattern (`keep_na = TRUE`) so that simulate-and-refit mimics the design; rows with NA keep valid parameters since the recorded parameters have `nObs` rows (guess that recorded parameters at NA rows are finite; to check).

11. **Return format.** moveHMM/momentuHMM return the full data frame including covariates and `states`; hmmTMB returns the input data plus streams, states as an attribute. For LaMa (no data frame, no covariates known) a list with `states` and one element per stream (vectors/matrices of length `nObs`, same names as `mod$streams`) and `nsim` replicates seems the natural analogue; the user can `cbind` it to their data. The `states` option corresponds to `states = TRUE` in the moveHMM family.

12. **Out of scope / do not copy:** measurement error and irregular sampling (`lambda`, `errorEllipse`), raster covariates, retries within a spatial extent, hierarchical models, hidden defaults (random `beta`, random `delta`, `nbCovs` noise covariates, silent recycling).

## Decision for the first version (from the user)

`simulate(mod)` returns data on exactly the observed design: same number of tracks, same track lengths, `Gamma`/`delta`/stream parameters fixed at the recorded values (i.e. conditional on the observed covariates).

Consequences (my reading, not from the packages; none of the three surveyed packages simulates CT-HMMs or MMPPs, so there is no precedent to compare with):
- **Discrete-time HMMs:** as in the items 1, 3, 4, 5 above; no covariate or design arguments needed.
- **CT-HMMs:** the reported `Gamma` slices are the transition matrices over the observed time gaps, so the simulation is conditional on the same irregular observation times. Simulating the sampling times themselves is not part of this step.
- **MMPPs:** not supported. The data are the event times, i.e. the design itself is random, so there is no fixed design to condition on (the state-process path would have to be simulated in continuous time and events drawn from it).
